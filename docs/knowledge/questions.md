# Open questions

## Q-001 — What implementation shape best supports durable exclusive ownership?

A per-user local daemon remains the recommended production hub for one durable lease ledger, shared consumer integration and bounded observations. The minimal per-invocation lock/journal alternative is compared in [architecture](architecture.md#minimum-safe-cross-worktree-reuse-design); it still needs process guardianship and conservative reconciliation. Queue authorized a bounded local prototype of the daemon candidate, described in [architecture](architecture.md#local-storage-prototype); that prototype does not select a production implementation. The selected host's proof that all slot writers and outstanding write capabilities end or are fenced, plus daemon failure/restart mechanics, remain open for qualification.

The reviewed [macOS readiness findings](qualification-readiness.md#process-containment) refuse process scans as descendant-complete proof. The follow-up compared inherited App Sandbox rights and Endpoint Security; neither supplies a reviewed fence for arbitrary descendants or unrelated same-user writers. Tom approved a narrower cooperative foreground-workflow contract; the fixed native fixtures and S1–S3 of the standalone Cargo workflow have qualified completion within that contract under Q-013. No permanent-quarantine fallback has been accepted as the product design.

## Q-002 — What exact toolchain and checkout-path portability can be supported?

Cargo 1.91 stabilizes `build.build-dir` and `CARGO_BUILD_BUILD_DIR`; this moves intermediates but does not prove cross-path reuse. Run 5 on pinned 1.97.1 reused the released slot at B with zero rebuilt units and tests executed, but its binaries retained A compiler source paths. The strict proof failed, and source/configuration/toolchain miss controls did not run. The logical-path candidate uses one identical complete map of consumer-owned roots registered before the first mapped build. Its permanent root-set identity is separate from each task's mutable source revision and exact-run receipt. The consumer proposal is a finite pool of task-worktree paths, allocated exclusively and returned only after normal workspace archive and exact source/evidence retention; [project adoption](contracts/project-adoption.md#stable-source-path-lifecycle) compares this with a separate stable compilation-source view. Current Queue task roots are unique and its Spec 028 build outputs stay private; Nucleus Contract 002 keeps task workspaces and branch identities separate. Neither consumer currently supplies a root pool, task-attempt authorization for Oxide acquisition or dirty-source snapshot receipt. These are proposed owner integrations, not shipped APIs. If the consumer cannot support that path lifecycle, stop finite-root remapping for ad hoc worktrees and leave the duplication problem unsolved. Cargo 1.97.1 fingerprints Rust-flag changes, so changing the map safely causes a cold partition; do not add roots opportunistically or discard such a partition and call it reuse. Old partitions remain subject to bounded, safe eviction. The only cited size, about 2.3 GiB of planning+diagnostics artifacts, used the line-tables profile; full-debug size is unmeasured. The map only remaps compiler source names, not behavior-bearing manifest/generated/runtime paths. Tom accepted logical compiler names with exact-run source mapping and the experimental qualifier implementation on 2026-10-10; [vision](vision.md#authority-boundaries) owns that ruling. Fixtures exercise resolver, flags and receipt rules only. The registered Cargo runner now has a test-only producer. Task 015 launched one owned Cargo invocation after the 014 TMPDIR rejection; the frozen fixture build script failed (`PathBuf` formatted with `Display` in `probe/build.rs:21`), tests did not run, and mapped reuse remains unqualified. Production keys stay checkout-isolated and no portability or daily-duplication benefit is established. Reassess at each supported Cargo/rustc upgrade; retire remapping only after shipped Cargo support passes the full qualification gate without the per-root map. See the [portability assessment](qualification-readiness.md#portable-source-identity-proposal-design-only-2026-10-09), [Cargo capability findings](rust-dx-landscape.md) and [storage architecture](architecture.md#minimum-safe-cross-worktree-reuse-design).

The current Oxide evidence path parses bounded hook rows, recomputes private binary/log digests, and binds receipts to policy/map/build identity, requested tree, lease and exact run/capture. Source, scanner, origin and behavior rows remain producer declarations. Task 017 added context-bound relative prefix mapping and an explicit full-debug `packed` fixture profile. Its cold-A Cargo test passed and emitted the accepted logical `file!()` and panic paths, but the preflight scanner stopped because several sibling `.dSYM` bundles made its selection ambiguous. That historical scanner searched all siblings instead of selecting the Cargo-reported executable's exact `<name>.dSYM`; the implementation and ordinary regression now select only that companion. The probe's Cargo rustflags are now encoded from the resolved map's ordered effective flags, with an equality regression. These code fixes do not change the original evidence or establish debug binding/full-debug source lookup; no new probe ran, and source invalidation and cross-path reuse remain untested. Any further probe requires a new scoped Queue record and fresh resources. The exact result, preserved evidence and resource bounds are in the [Task 017 execution record](qualification-readiness.md#task-017-execution-result-2026-10-10) and [registered Cargo source-map schema](qualification-readiness.md#registered-cargo-source-map-evidence-schema).

## Q-003 — What partitions, budgets and reconciliation proofs are sufficient?

The design recommends distinct compatibility-partition and per-run identities; durable idempotent acquire/reconcile/finalize; refusal for concurrent or uncertain claims; and proven-idle-only eviction. A later ruling settled the 20 GiB host free-space rule as a monitored start/abort threshold, not a guarantee. Fixed native fixtures enforce a small task-owned bound; the standalone Cargo pilot's approved 8 GiB image and host-threshold controls passed independent review for S1–S3 under its 10 GiB disposable ceiling. This does not qualify production capacity policy, arbitrary output coverage or write volume. Production host locking/process containment and later product budgets remain open. See [the ownership protocol](architecture.md#semantic-operations) and [budget policy](architecture.md#budget-and-observations).

Reviewed [capacity findings](qualification-readiness.md#temporary-output-must-be-in-the-10-gib-footprint) include temporary output in the disposable footprint and distinguish sampled aborts from kernel enforcement. The host reserve policy is settled in Q-014. The separate enforced disposable-footprint cap remains a prerequisite.

## Q-012 — How does the consumer bind task admission, storage acquire and host-run scheduling?

The proposed [stable source-path lifecycle](contracts/project-adoption.md#stable-source-path-lifecycle) recommends a bounded consumer-owned pool of task-worktree paths, but Queue/Nucleus currently have no such pool or Oxide task-attempt credential. Their managed-Git/worktree and lifecycle owners must approve concrete opt-in fields, canonical path assignment/recycling, exact dirty-source retention, and the authenticated task/workspace/run/attempt-to-root binding. The consumer must wait without an Oxide lease or host-run slot, then authorize acquire before host-run submission. An acquire `busy` response must return the authorized request to consumer-owned pending state without creating or settling a host run; read-only inspection found no current task-attempt-to-acquire/return transition, so that narrow lifecycle representation needs owner approval. After successful acquire the adapter submits through the existing heavy host-run scheduler, which alone issues its token and owns admission, launch, cancellation and settlement. Frozen Contract 010 stays unchanged; no host-run storage-busy settlement or forged token is proposed. Queue and Nucleus host-run/workspace owners must separately confirm the mapping against Queue's existing implementation and Nucleus Contracts 002/010. Fixture behavior and the standalone local pilot do not establish these APIs or real consumer portability. Adoption, real-project qualification and rollout remain gated; Task 017's full-debug companion/source lookup is still insufficient and production keys stay checkout-isolated.
